Website implementation artefacts

Application stack

The source repository uses Next.js, React, TypeScript/JavaScript, Auth.js credentials authentication, Prisma, and PostgreSQL. It also integrates Cloudflare R2-compatible object storage for private media assets and Nodemailer for configurable password-reset email.

Data model

The Prisma schema defines users, organisations and memberships, creators, projects, content items, tasks, assets and versions, reviews and comments, notifications, audit logs, password-reset tokens, and rate limits.

Workflow and access

The application code includes authenticated dashboard routes and API handlers for projects, tasks, and assets, with role- and organisation-based access checks. The UI supports project and content workflow, assignments, asset handling, review comments, notifications, and account settings.

Release and testing evidence

The repository includes hardening, workflow, and backend test scripts plus production-readiness documentation. The latest release audit records that code-side fixes were reviewed, while deployment, production database migration, SMTP delivery, Cloudflare configuration, and authenticated production checks still require external verification.

Deployment note: The repository documents www.setups.nexus as the intended canonical production origin. A repository configuration or intended domain is not, by itself, proof that the live production release is fully deployed and verified.

1. Agile Team Charter

Project purpose and vision

Nexus Setups is a creator-focused service concept that provides video editing, thumbnail design, and SEO/tag optimisation. The project aims to help creators receive consistent content support through clear service packages, organised project tracking, review and revision workflows, and reliable client communication.

Vision: Establish Nexus Setups as a reliable, organised creator-support service that helps creators improve the consistency and presentation of their content.

Objectives

  • Define the business model, target audience, value proposition, pricing, and success measures.
  • Build a recognisable brand and website explaining the service.
  • Provide secure account access and a client portal.
  • Allow clients to submit projects, upload assets, and track progress.
  • Establish editing, quality assurance, revision, delivery, and communication workflows.
  • Support quotes, invoices, payment tracking, administration, and analytics.
  • Test the service, document it, and prepare for launch.
  • Keep legal and compliance responsibilities visible until completed.

Scope

Included: business planning, branding, website, authentication, client portal, project management, editing workflow, communication, payments, marketing, administration, testing, documentation, and launch preparation.

Outstanding legal/compliance work: Register Nexus Setups as a Business; Register for Tax (SARS); Secure Business Insurance. These are not treated as complete.

Evidence

Planning evidence includes Trello cards such as Define Business Vision, Create Business Model Canvas, Design Homepage, Implement User Registration, Create Client Dashboard, Submit New Project, Define Editing Workflow, Implement Invoicing System, Implement User Management, and Conduct Beta Testing. Implementation evidence can be inspected in the Nexus Setups source repository, including the Prisma schema, authenticated dashboard, and API routes for projects, tasks, and assets. These code artefacts demonstrate implemented application structure and logic; they do not by themselves prove a complete live production rollout.

The related application repository provides a second kind of artefact: implementation evidence for the actual Nexus Setups website. The Trello board shows the intended scope and breakdown of work; source files show how selected parts, such as authentication and project data handling, have been implemented. These sources serve different purposes and should not be treated as interchangeable proof.

Reflection

The charter shows that Nexus Setups is both a creator-support service concept and a software platform. The Trello board captures the planned service lifecycle, while the application repository provides more concrete technical evidence for authentication, organisation-based access, projects, content, tasks, assets, reviews, notifications, and administration. A key lesson is to distinguish a planned backlog item, code implemented in the repository, a feature verified in a running environment, and a production-ready business. Legal readiness and external release configuration must be tracked separately from code implementation.

  • The client can see confirmation or track status.

Example: Editing Workflow — proposed acceptance criteria

  • Work moves through intake, editing, review, revision, and delivery.
  • Ownership and status are visible.
  • A quality check takes place before delivery.
  • Revision feedback is recorded.
  • The final deliverable can be handed over to the client.

Reflection

User stories connect the backlog to visitor, client, editor, and founder needs. A feature is valuable when it solves the user's problem, not merely when a form or screen exists. Acceptance criteria make “done” specific. Future refinement should add measurable acceptance criteria, priority, estimates, and owners before work enters a sprint. The acceptance criteria above are proposed checks, not claims that these exact checklist items appeared on the Trello cards.

Retrospective: what worked in the plan

  • The board breaks the service concept into 13 named work areas.
  • User stories connect tasks to client access, project submission, editing, invoicing, and launch testing.
  • The backlog includes both customer-facing capabilities and supporting operations.

Areas to improve

  • The CSV is a task export, not proof of completion on a particular date.
  • Historical sprint dates, decisions, blockers, estimates, and review outcomes are not reliably evidenced.
  • Legal/compliance work needs an owner, required evidence, and a verified completion check.
  • High-impact features should have measurable acceptance criteria and dependencies.
  • Real progress tracking should distinguish planned, in-progress, complete, and blocked work.

Actions for a future iteration

  1. Record a dated sprint goal and selected work at the start of each sprint.
  2. Add owners, effort estimates, and acceptance criteria.
  3. Capture blockers, decisions, and scope changes as they happen.
  4. Record sprint review feedback and retrospective actions.
  5. Track turnaround time, revision frequency, client satisfaction, lead conversion, and payment status.
  6. Verify business registration, SARS tax registration, and insurance before marking legal/compliance readiness complete.

Reflection: Nexus Setups connects a Trello-based project plan to a real application codebase. The six-month task dates are reconstructed estimates; code presence, feature verification, production deployment, and legal/compliance readiness are separate claims and should not be conflated.
