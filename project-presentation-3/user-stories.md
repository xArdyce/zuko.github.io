## Purpose

A user story describes a capability from the perspective of the person who needs it and explains why it matters. The supplied Trello cards use the pattern “As a [role], I want [capability] so that [benefit].” The task title and description define the work to be carried out.

## Example task breakdown: submit a new project

**User story:** As a client, I want to submit a new project so that the Nexus Setups team can begin work.

**Possible acceptance criteria**
- A client can enter the information needed to describe the project.
- Required deliverables and relevant deadlines can be recorded.
- The client can provide or upload relevant project assets.
- The submission is visible to the team and can be assigned for work.
- The client can see that the project has been received or track its status.

These acceptance criteria are a proposed way to verify the story. They are not represented as checklist items recorded on that specific card.

## Example task breakdown: editing workflow

**User story:** As an editor, I want a clear workflow so that I can deliver high-quality content efficiently.

**Possible acceptance criteria**
- Work moves through clear stages from intake to editing, review, revision, and delivery.
- Ownership and current status are visible.
- A quality check takes place before delivery.
- Revision feedback is recorded and can be acted on.
- The final deliverable can be handed over to the client.

## Reflection

User stories connect the project backlog to the needs of visitors, clients, editors, and the founder. For example, a project-submission feature is not valuable simply because a form exists; it is valuable when a client can provide enough information for the team to start work and follow the project. Acceptance criteria make the meaning of “done” more specific. In a future iteration, I would ensure each story has measurable acceptance criteria, a priority, an estimate, and a clearly assigned owner before it is selected for a sprint.
